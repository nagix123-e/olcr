This is an evidence ledger for [the repository-aligned implementation plan](OLCR_UNIFIED_ARCHITECTURE_IMPL_PROMPT_V3.md). OpenCV feature-by-feature adoption decisions and the adaptive-frame-rate split are recorded in [the OpenCV plan reconciliation](OPENCV_PLAN_RECONCILIATION.md).

The registered thread goal is an umbrella for this implementation, but its visible objective does not spell out the chat-first product contract. The CX gates below and in V3 are therefore binding goal-completion criteria: finishing the component checklist or a Studio-only workflow cannot complete the goal while ordinary users still cannot start and control the requested work from chat. The umbrella goal is active and remains open until its engineering and chat-first acceptance evidence is complete.

## Chat-first product experience

The desired entry point is chat for starting and controlling Web scraping, browser E2E and native Computer Use. Settings are a policy surface for capability enablement, target/origin scope and OS permission status; they must not be a required workflow launcher. This is a new cross-cutting acceptance overlay in addition to P0–P30 and V/A/R/W/U, defined in the [V3 plan](OLCR_UNIFIED_ARCHITECTURE_IMPL_PROMPT_V3.md#product-acceptance-overlay-chat-first-computer-use-and-web-scraping) and indexed in the [readiness matrix](OLCR_UNIFIED_READINESS_MATRIX.md#chat-first-product-acceptance-overlay).

### Current user-visible process and gap (checked 2026-10-04)

- **Web scraping:** with `web_scraping_enabled` ON, a chat request containing one explicit HTTP(S) URL opens a managed Playwright session and embeds a screenshot viewport plus task card in the same conversation. While a scrape run is active, the viewport refreshes every 2.5 seconds. OLCR drafts a visible-DOM Recipe and starts `ScrapeRunManager` only when existing Preview & Validate passes. If drafting/validation fails, chat asks for a focused clarification; the next free-form reply reuses the same browser session and retries the same Recipe validation path. During that pre-run clarification, chat can now resolve “go to the next page” against fresh, filtered controls and select one unique same-origin link or allowlisted read-only reveal button; it still revalidates at dispatch and asks when ambiguous. Chat supports scrape status/pause/resume/stop/results/export. The screenshot viewport itself is not a direct click surface, arbitrary public-page actions remain outside the read-only allowlist, and actions after a ScrapeRun starts are not routed from chat. Scrape Studio remains available for detailed repair. Public live-site behavior and multi-run clarification remain open.
- **Local browser E2E:** with `local_e2e_enabled` ON, the current conversation's allowed project supplies the workspace. Chat can attach to a provided loopback URL or start `.olcr/e2e.json`, one supported package script, or a user-supplied shell-free command bound to one loopback host/port. The managed Playwright viewport and task lifecycle stay in chat. A natural-language plan already passed one isolated live selected-model journey with visible effect verification. This is the closest complete path; broader target/command clarification, reliability, and recovery evidence remain.
- **Native Computer Use:** with `computer_use_enabled` ON and the target app's bundle ID in the Settings allowlist, chat can start capture for a running app or launch a closed one by exact bundle ID. Settings supports adding a closed target by bundle ID; the native bridge resolves it through Launch Services, the backend independently rechecks enablement and scope, then chat waits for the app's live PID before binding ScreenCaptureKit. An unknown display name for a closed app is not guessed. Listing running app names and bundle IDs does not need Accessibility trust; AX permission is still required to inspect or operate controls. Native chat accepts labelled disclosure expansion, menu-grounded Find/Search, uniquely grounded button actions, outcome-derived button goals, explicit sequences of two to four supported steps, and bounded text entry into a uniquely identified visible/enabled non-secure AX text field/area. If needed, the native bridge focuses that exact target via AX, confirms focus, replaces the field value, and verifies a private AXValue readback without returning the value; planner/API/frontend/native compile checks pass, while live GUI acceptance of the focus-first path remains open. Every dispatched step re-observes, plans, executes, and verifies with progress in chat. A bounded wheel-scroll action now targets one unique visible AX scroll area and its geometrically associated vertical scrollbar, revalidates target PID/session/window and scrollbar value natively, sends a small wheel event to that PID, and requires a fresh same-session directional scrollbar-value change. The selected visible enabled AXButton prefers AXPress; when AXPress and usable AX geometry are unavailable, chat can request UI-Venus grounding and the existing OpenCV/Apple Vision frame-pair tracker. The same guarded route moves the native pointer in bounded sampled steps, then requires a fresh same-PID/bundle AX observation of the exact visible target and a point still inside its control and window frames before dispatch. The chat preview displays the sampled pointer position and remaining distance. Run `20261003-220000-scrollfix` remains the latest live click evidence; wheel scrolling and the new staged movement path have focused tests but await GUI acceptance. **Current action boundary:** arbitrary key presses beyond the menu-grounded Find and Tab routes, drag, and AX-free canvas/game clicking are not accepted. Autonomous action loops stop after the bounded four-step goal planner; reconnect/resume, multi-display calibration, and window-movement recovery remain unaccepted. A previous isolated OLCR test app/backend was still running during this audit, so no new GUI run was started under the repository's identity-safety precondition.
- **Settings boundary:** capability toggles and app/origin/workspace scopes use field-specific updates so concurrent saves do not replace unrelated policy state; Computer Use scope rejects OLCR's own bundle ID. Settings contains capability/scope and OS-permission setup only, including Screen Recording status, an explicit one-time request action, and refresh. Chat capture startup only checks the current OS grant and reports how to resolve a missing grant; it never raises a permission request as a side effect of each task. Observation, monitoring, World State inspection, capture telemetry, and manual UI-Venus grounding live in the separate Desktop diagnostics surface, outside Settings. Existing `BrowserSessionManager`, Playwright executor, Recipe/ScrapeRun, `LocalE2EManager`, ScreenCaptureKit, AX, APC, OpenCV, UI-Venus, and action verifier remain the implementation boundary; no parallel runners were added.

```json
{

}
```

## Scrapling / Playwright boundary decision

- The source plan assigns Scrapling to HTML extraction (most directly W1's URL → HTML → main-content → Markdown pipeline) and Playwright to browser lifecycle and automation. The existing implementation follows that split at the browser layer: managed Playwright owns Chromium sessions, login-capable contexts, navigation, live DOM/accessibility evidence, element picking, Recipe selectors, and same-origin network-response inspection. Those flows already have selector alternatives and human-reviewed accessibility snapshots; adding Scrapling there would create a second browser/DOM recovery path over the same evidence.
- Keep the existing bounded, SSRF-safe pinned fetch as the network boundary. Treat Scrapling only as an optional parser/extraction adapter for static HTML responses in W1, never as a second browser runner or as the owner of interactive Scrape Studio sessions. Do not use Scrapling's fetcher to bypass the existing pinned-fetch safeguards.
- Current decision: do not add the Scrapling runtime dependency yet. The evaluated basic parser did not beat `_Text` on the three offline fixtures; the richer extraction path was not shown equivalent to OLCR's safe fetch/metadata/budget contract; and its current package Python floor conflicts with OLCR's Python 3.9 declaration. Keep W1 PARTIAL and revisit the adapter only after a representative corpus comparison demonstrates a measurable quality gap that survives the existing parser improvements and a compatible dependency/runtime decision. W2–W16 remain Playwright/Recipe responsibilities; no new extraction or selector engine is justified there.
