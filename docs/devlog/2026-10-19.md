# 2026-10-19 — 会話ごとの並行実行と表示分離

## 変更

- フロントエンドの履歴、入力、添付、カスタムエージェント、エラー、実行状態、GUI操作進捗を `(project_id, conversation_id)` 単位で保持する。非同期コールバックの書き込み先は送信開始時に固定し、他の会話へ移動しても実行を継続する。
- 会話を選択した時点で表示対象を切り替える。未取得の履歴は読み込み表示にする。メッセージ領域と入力コンポーネントに別々の会話別Reactキーを付け、以前のDOM、タスク表示、音声入力状態を再利用しない。
- 履歴取得とポーリングは会話ID、選択世代、状態の改訂番号、実行状態を確認する。古い応答が生成中の文や別会話の表示を上書きしない。
- 新規会話はリクエスト前に確定する。作成待ちに移動した場合も元の送信を背景で継続し、移動先を奪わない。入力と概念図の下書きを確定した会話へ引き継ぐ。
- 会話一覧はプロジェクト単位で保持し、実行中の会話を表示する。実行中の会話の削除ボタンを無効にする。
- ストリームの停止先と停止予約を会話単位にする。別の会話の完了・エラーで停止先を解除しない。コーディングタスク通知と再通知も発生元の会話に限定する。
- モデル設定と設定エラーは会話単位で表示する。背景の完了処理は使用量だけを更新し、現在の会話の設定取得を無効化しない。
- モデル呼び出しに会話横断の排他は追加しない。遅延評価されるストリームのフォールバックにも、元の会話のモデル設定を固定する。使い終わったストリームは閉じる。
- HTTP 409/429/503の本文が明示的に同時実行の拒否を示す場合に `MODEL_CONCURRENCY_LIMIT` として説明する。通常のトークン上限を同時実行拒否とは判定しない。プロバイダーの本文は画面へ転記しない。
- フォールバックの通知はリクエストの言語を保持し、利用上限だったと断定しない。同一GUIを操作するComputer Useと同じ作業ディレクトリの実装実行には、それぞれ既存の資源制約がある。通常チャットの並行実行を止める制約にはしない。

## 確認

- フロントエンド: 8ファイル、103件成功。実際のAppをDOMへ描画し、2会話のストリーム、新規会話の作成待ち、添付付きREST返信、エラー、遅延履歴を交互に到着させて表示と下書きの分離を確認した。会話を切り替えた直後、履歴取得前にも旧メッセージが存在しないことを確認した。
- バックエンド: 39件成功。一時DBを使うBrain API、モデル設定、プロバイダー、並行実行のテストを実行。同一モデルの2リクエストをバリアで同時待機させ、両方が進行し、応答と保存履歴がそれぞれの会話に留まることを確認した。実モデルや外部APIは呼んでいない。
- 最初の広いバックエンド実行では、デフォルトDBへの書き込みとOAuthコールバックのソケット待受がサンドボックスで失敗した。DBは以後一時プロファイルへ隔離し、今回の変更と無関係なOAuthコールバック試験1件は対象外とした。
- 既存のBrain API試験は、古いOrnith選択が現在のMLX配置に移行される仕様に合わせ、モデルごとに新しい応答辞書を返すfixtureへ更新した。
- TypeScriptチェックとフロントエンド本番ビルドを実行。ネイティブGUI、実モデルによる同時推論、インストール済みアプリへの反映は今回の確認対象に含めていない。
