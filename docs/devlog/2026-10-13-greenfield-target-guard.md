# 新規作成工程の TARGET_NOT_FOUND 誤判定

## 確認した実際の停止原因

対象は専用プロファイル `olcr-latest-20261013-2112-orchestrator-audit-retry-profile` の Task `7942438c-76af-4f2b-b074-3cddab373208`。DBは読み取り専用で参照した。

起動ログには `IMPLEMENTATION_SCOPE_SOURCE=PLAN_MANIFEST FILE_MANIFEST_COUNT=6` に続いて `FILE_FINAL_STATUS=TARGET_NOT_FOUND` があり、`MODEL_RAW_RESPONSE_KIND` や実装モデル呼び出しはない。runtimeはモデルを呼ぶ前に完了状態で返していた。

前回の修正で元の依頼全文を実行契約へ渡すようになった結果、依頼末尾の「失敗があれば修正してください」と先頭の `index.html` が、直接チャット用の既存ファイル編集ガードに一致した。空のプロジェクトなのでファイルはまだ存在しない。これをモデルの説明だけの出力と誤分類し、同じ前処理を再試行した。

2回の停止通知は、ログ上ではユーザーの明示的GUI再開を挟んだ recovery epoch 0 と 1 の停止である。同じ停止イベントの二重保存という証拠はなく、両方とも同じ前処理の誤判定が原因だった。

## 修正

- managed implementationでは既存ファイルを要求する自然言語の事前ガードを適用しない。承認済みmanifest、PathGuard、操作のpreflightは引き続き全操作へ適用する。新規ファイルはwrite、存在しないファイルへのpatchは拒否する。
- 通常の既存ファイル編集で対象がない場合は、`TARGET_NOT_FOUND` のtyped拒否記録とFAILED状態を返す。成功やモデルの説明だけの出力として扱わない。
- 変更が必要な工程で操作のない終了をPASS報告にしない。
- 未分類のDone/Verify項目は、PASSという報告形状だけでは満たされたことにしない。実行操作がゼロなら未達にする。これは汎用条件の完全な意味検証を実現するものではない。
- テスト0件を終了コード5で返すPythonでも、停止理由を「テスト0件」として記録する。

## 検証

新たに5件の回帰テストを追加した。元の依頼に「失敗があれば修正してください」を含む空プロジェクトで、実Runtimeが実装モデルを1回呼び、承認されたHTMLとJSを作成・読み戻すことを検証した。モデル応答は決定的なテストダブル。manifest外へのwrite拒否、通常の欠落ファイル編集のtyped失敗、操作0件のFAIL報告と未達評価も確認した。

関連13モジュールは313件実行、5件スキップ、残りは合格。ログ: `/private/tmp/olcr-greenfield-final.log`。差分の空白チェックも通過。

初回の広い実行では通常Web検索の既存テスト2件も失敗したため、関連313件から除外した。これらは今回変更した実装・報告・評価経路を呼ばないことをガード付き再実行で確認した。ログ: `/private/tmp/olcr-greenfield-unrelated-web.log`。Web検索の問題は今回修正していない。テスト0件の終了コードに依存した既存fixture、および操作証拠のないMCP sentinel fixtureは実際の契約に合わせて更新した。

稼働中のユーザーTask・成果物・プロファイルは変更していない。起動中のアプリにはこのソース修正はまだ反映されていない。実生成モデルによる昼食ルーレット全工程の完遂、GUIの再起動・再確認は未実施。
