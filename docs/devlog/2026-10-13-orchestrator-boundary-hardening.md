# オーケストレーターの実行境界の再検証

2026-10-13。新規作成の TARGET_NOT_FOUND 誤判定を受け、元の依頼、工程説明、再試行診断、生成コードが制御命令や実行証拠として誤解釈される箇所を調べた。既存GraphifyグラフでRuntime/実行契約/復旧の関係を確認し、現行ソースを直接読んで修正した。

## 修正内容

| 問題 | 修正と検証 |
|---|---|
| managed工程の説明に credentials / sudo / rm -rf があるだけで通常チャットの拒否へ流れる | managed実装は型付き契約から直接ファイル実行器へ渡す。実際の操作はmanifest・PathGuard・preflightを通す。禁止事項の記述で実行先が変わらないことを確認 |
| run local script / rename file / write file / procedure lowercase の説明が直接操作ルートへ流れる | 同じ型付きdispatchで通常チャットのコマンド解釈を通さない。5種類の説明文でファイル操作を確認 |
| 元の依頼にある計画承認前の「実装しない」が、承認後も停止条件になる | hostの boolean global_no_write が明示されている場合はその値を使用。trueは禁止、falseは承認済み実行。欠落した古い呼び出しは既存の禁止判定を保持 |
| managed契約のworkspace欠落・未知のintent・文字列のfalseが通常Brainへ流れる | 契約を実行前に検証。曖昧な値をbooleanへ変換せずFAILED。通常Brainを呼ばないことを確認 |
| JavaScriptのcontinueや、ファイル内容の「続行しますか」が続行要求として拒否される | operations内のコードを制御判定から外す。文字列の応答メタデータだけを確認 |
| 文字列・コメント・正規表現内の括弧で合法なJavaScriptが拒否される | Nodeの構文検査をコード非実行で使用。TS/JSXはJS用の括弧数判定をせず、プロジェクトの検証へ委ねる |
| 静的HTMLにない動的要素やoptional DOM lookupを拒否する | 静的IDの存在推測を実装拒否の条件から外す。実際の動作は検証工程へ委ねる |
| 同一内容の短いファイルを再度writeすると置換長の保護に拒否される | 内容が変わるwriteだけに置換長の保護を適用。同一内容の再実行は既存のidempotent診断へ渡す |
| 200件の一覧制限で承認済みの既存ファイルがSOURCEから落ちる | 承認対象の既存ファイルは制限外でもsnapshotへ追加。外部を指すsymlinkは一覧・ソースから除外 |
| backend/index.jsがfrontend/index.jsの存在証拠になる | ディレクトリを含むパスを一致させる。裸のbasenameは一意な場合のみ対応付ける。複数ファイルの条件から未記録のファイルを落とさない |
| workspace_listだけでUIの確認項目が満たされる | 一覧・準備・no-op候補だけの操作を汎用条件の成功証拠にしない |
| 修復後も以前のpermission/deniedが成功を止める | 過去の成功操作は保持する一方、権限・拒否の停止判定は現在の試行で評価。現在の拒否は引き続き止める |
| 明示的VERIFICATION_ONLY工程が実行可能な検証を持たずファイル実装へ流れる | 完了済み工程を保持し、既存の回数制限内で検証契約を再計画する。ファイル実行器を呼ばない |
| 報告の形式修復モデルがtest_passやchanged_files等を書き換えられる | 形式修復をhost側の決定的処理へ変更。モデル呼び出しなしで、既存の実行証拠を保持して配列・識別情報・欠落した容器だけを修復 |

- 範囲外ファイル拒否、欠落ファイルへのpatch拒否、失敗時rollback、ゼロ件テスト拒否、再開・停止・スケジューラー、完了判定の既存テストも実行。

前回から既知の通常Web検索テスト2件（`test_api_miss_uses_brave_even_for_vague_prompt_without_lookup_verbs`, `test_automatic_information_lookup_uses_brave_then_inference`）は今回の412件から除外した。前回、変更した実装経路を通らずに同じ失敗を再現することを確認済み。このWeb検索問題は修正対象外で、全バックエンドテストが合格したという結果ではない。

## 確認の範囲と残る制約

モデル応答は決定的なテストダブルを中心に検証し、実Runtime・ファイル実行器・Node/Python検証器を使用した。実生成モデルによる昼食ルーレット全工程の完遂やGUI再確認はまだ行っていない。起動中アプリへのソース修正反映には再起動が必要。

Nodeが見つからない場合や構文検査器が起動できない場合、推測でソースを不正とは判定せず、宣言された検証器による確認が必要になる。TypeScript/JSXもプロジェクトの検証器が必要。静的ソースだけでUI動作の正しさを証明したという扱いにはしない。

古い計画の互換経路には自然言語による工程種別推定が残る。今回の検証専用工程の流入防止は明示的VERIFICATION_ONLYを対象とする。汎用Done/Verifyの全内容を意味的に証明する検証器や、外部モデル・外部サービスの可用性保証を追加したものではない。
