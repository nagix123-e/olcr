# Coding verification and repair lifecycle

The persisted manual task reached its browser acceptance stage but repeatedly
rewrote source using an earlier input-capability diagnosis. Its current source
had a separate defect: pure-module loading had been repaired by removing browser
initialization/event wiring. Completed clicks then produced no visible state
change. Reusing the old diagnosis could not repair that defect.

Common controller corrections:

- Re-execute cached acceptance checks against current manifested source before
  choosing a writable repair. Preserve passing checks and re-author only failing
  checks whose ownership belongs to the verifier.
- Bind a cached source-defect review to source digests, failing check programs
  and observed failures. An unchanged failure can reuse its review; changed
  source or a different remaining failure must be reviewed again.
- Clear transient defect/diagnostic flags at each preparation boundary. A prior
  failed report alone cannot authorize a new host-owned source repair.
- Preserve the prepared verification command/targets/host contract when changing
  execution mode. Merging the original phase previously overwrote a generated
  browser runner with its old Node-only command.
- Keep actual project-test/resource/browser executor failures separate from
  generated assertion defects. Carry the current command output into repair;
  an unavailable executor does not authorize source edits.
- Review application failures even when another check also has an API error.
  One bad check must not hide a real implementation failure in the same batch.
- Repeating already-preserved checks is not coverage progress. Reject those
  responses within the existing bounded authoring budget; resuming unchanged
  task/source cannot restart the same failed authoring loop.
- Record bounded before/after page observations around real clicks. A click
  completing is not evidence that the application's event handler ran.
- Repair guidance explicitly preserves entrypoints, initialization and event
  handlers when making shared code importable in another runtime.
- A real-model run on an unrelated character-counter app uncovered another
  verifier-owned stop: generated checks redeclared a supplied binding and split
  a quoted JavaScript literal across lines. Repeated code generation could not
  recover. After a syntax failure, switch to typed observations compiled by
  OLCR instead of asking the model to emit more JavaScript. This transport can
  observe DOM/file facts, execute actual module exports, read JSON properties,
  and run registered project tests. A successful replacement still receives
  an independent semantic review; compilation alone never proves coverage.
- Versioned contracts retain earlier passing checks through this upgrade.
  Resuming the isolated task reuses its original files and recovery counters.

The isolated native audit accepts `--request-file` and snapshots the request in
its own temporary profile, allowing unrelated tasks to exercise the same flow.
It retains the current model deployments and never operates on the user's app
database or workspace. No benchmark-specific repair was added for this change.

Additional recovery hardening from the same unrelated audit:

- Reject string values for boolean observations and string values for click
  actions at grammar generation time. The compiler validates the same types.
  Viewport actions accept bounded numeric dimensions so a mobile check can
  exercise the required width rather than merely inspect the default viewport.
- Mechanical test-command exit/output criteria use owned test execution even
  when mixed with browser criteria. Full-match recognition deliberately excludes
  additional behavioral requirements, which still need independent checks.
- Contract version 17 migrates passing checks from versions 16–13. No recovery
  budget was reset to complete the audit.
