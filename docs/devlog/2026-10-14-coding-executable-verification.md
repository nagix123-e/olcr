# 昼食ルーレットの停止ループ：実データと実モデルによる調査

## 調査方法

- Graphifyの既存グラフから計画・実装・検証・再開の関係を参照し、現在のソースを確認した。
- 添付された会話と、起動済みの隔離OLCRプロファイルにあるTask・工程レポート・ログを読み取り確認した。
- ユーザーのTaskと成果物は変更せず、計画・承認範囲・復旧epoch・工程レポート・宣言されたファイルを `/private/tmp` の専用プロファイルへコピーした。
- 再現では実際のBonsaiモデル、Runtimeのファイル操作、同梱Node.js、実Chromiumを使用。外部のデバッグ情報取得だけを無効化した。
- モデル応答を固定した回帰テストと、実モデルの再現結果を区別する。回帰テストの件数だけで実モデルの完遂を主張しない。

## 原因

| 境界 | 実際に確認した問題 | 修正 |
|---|---|---|
| 計画 → 実装 | 自然文の「Node.jsでimportして確認」が、実行可能なコマンドを持たないまま工程の完了条件になっていた。実装モデルの操作プロトコルはファイル操作で、コマンドを実行できない | 依存なしHTML/JavaScriptの統合検証を最終工程へまとめ、別途生成した検証コードをOLCRのNode.js/Chromium実行器で実行する |
| 実装 → 工程判定 | ファイル作成・読み戻しだけでブラウザー操作や関数実行も成功扱いになる場合があった | 実行記録を必要とする。ブラウザー条件にはBROWSERチェックを要求する |
| ファイル名の解釈 | `package.json` が正規表現の選択順と終端条件により `package.js` として解釈され、存在するファイルを不足扱いにした。空白入りの絶対パスも分割された | 拡張子の境界と正確な既知パスの優先照合を修正 |
| テスト作成 → 実行 | テストコードを作る工程にテスト実行の完了条件があり、最終検証へ到達できなかった。テストファイル名に `test` があるだけで実行を要求する判定もあった | 作成物の存在・書き込み証拠と、実際のテスト実行を分離する |
| Node.jsの結果 | Node 20では空のテストファイル自体が1件の成功として数えられる | 実際に登録されたテスト名と終了コード・件数を確認する |
| モデル → ファイル操作 | Bonsaiのネイティブworkerへ構造化出力のformatが渡らなかった。JSON完成後も生成を続けたり、無効なJSONの診断情報を失ったりした | formatを渡し、JSON Schemaで生成トークンを制約する。完全なJSONオブジェクトで生成を終え、失敗応答・parse error・生成量を内部プロファイルへ保存する |
| 再開 → 進捗 | 保存済み証拠の再評価がPASSでも進捗がDONEにならず、再試行中に複数の工程がRUNNINGになる可能性があった | PASSの昇格時と再試行前に進捗を同期する |
| 再計画 | 検証コマンドや実行器だけを直しても、工程シグネチャが変わらず再計画を無効と判定できた | コマンド・対象・実行器を比較対象へ含める |
| 検証の生成 | 同じ条件を複数のチェックで検証するとエラーになった。必要な条件の不足がIDなしの曖昧なエラーだった | 重複を許容し、全条件の網羅を要求する。不足IDを報告する |
| 検証自身の失敗 | 検証コードの未定義ヘルパーなどをアプリの不具合として修正しようとすると再試行が収束しない | 検証コードの生成・構文・実行時エラーを区別し、検証コード自身の再生成へ戻す |
| チャットの追加指示 | 条件IDが同じままユーザーの要求が変わると、古い検証を再利用できた | 検証プロンプトとキャッシュ識別子に元の依頼と追加指示を含める。実装の修正だけでは同じ検証を維持する |
| 停止 | 検証コードの生成例外が未処理だと、RUNNING表示を残せた | 理由・生成診断・進捗を保存して再開可能状態にする |
| オフライン指定 | 「ネットワーク接続は使わない」という日本語を外部デバッグ検索の抑止が認識しなかった | 「使わない」「使用しない」「利用しない」を認識する |
| MLXの長い入力 | 実再現で14,680トークンの入力時、20,688,230,400バイトのMetalバッファ要求が20,100,448,256バイトの上限を超えてworkerが失敗した | 同梱mlx_lmのprefill手順と同様に512トークンずつキャッシュを評価し、最後の入力トークンを生成に渡す。処理済みトークン数を記録する |
| 修正の診断 | モデルが非asyncのIIFEへawait importを入れた。構文検証は止めたが、具体的なNode構文エラーがなく、その後の検証失敗で実装エラーが上書きされた | 構文エラーの行・種類を保存し、実装エラーを維持する。正しいJSONでも生成応答を内部保存する。packageのESM設定とCommonJSソースの食い違いを明示し、既存ファイルの末尾の操作例をpatchにする |
| 再試行回数 | 検証コード自身の修正が実装修正の枠を使い、実際の確認項目が改善していても一律の回数で再計画した | 検証生成の構文・API・意味の検査と限定された修正を、ソース修正前に行う。実際の成功条件・テスト成功数の最高値が改善し、ソース変更も保存された場合だけ実装の枠を追加する |
| 進展なしの判定 | 読み取り専用の検証失敗まで「変更がない実装」に数えた | 検証を実装の無進展判定から除外する。実装の変更拒否・ロールバックは判定を維持する |
| 元仕様の脱落 | 計画の完了条件だけを検証すると、ユーザーの6仕様の一部を検証しないまま終了できた | 明示された仕様セクションの箇条書きをブラウザーでの最終検証へ直接追加する。古い検証結果は新しい条件の証拠にしない |
| 長時間のworker通信 | 回帰テスト中にselectのFD上限エラーが発生し、JSONエラー扱いになった | DefaultSelectorへ変更する |
| モデル出力の文法 | JSON Schemaをプロンプトへ渡しても、実モデルが複数操作の境界を壊して終了した | 既存のllguidance 1.8.0で、Bonsai・Ornithの生成トークンへJSON Schemaのマスクを適用する。不正な構造を許すプロンプトだけの対策を置き換える。意味・JavaScriptの構文・操作範囲は実行側で引き続き検査する |
| 出力量 | 長い実装用モデルでも通常の2,048トークン上限が適用されていた | 実装対象数に応じて4,096〜16,384トークンの出力量を渡す。JSON完成時に終了し、未完了の場合は部分操作を適用しない。終了理由と生成量を保存する |
| 互換呼び出し | オプション引数のTypeErrorで別のモデルへ呼び直す経路があった | 呼び出し前に対応引数を確認し、選択済みのモデルを保持する。プロバイダー内部のTypeErrorでは再呼び出しをしない |
| モデルの入力 | 実装の制御文にOLCRという文字があるだけで、無関係な自己説明を注入した | ファイル操作契約ではプロジェクトの実装コンテキストを使い、通常チャット用の自己説明を挿入しない |
| モデル選択 | 新規アプリの依頼末尾にある「テストに失敗したら修正」を、依頼全体が小さな修正であると誤判定した | 新規作成の主目的と、工程自身の修正意図を区別する |
| 無変更の修正 | 変更前後が同じパッチの受付数を、実際の進捗に数えた | 無変更を進捗から除外する。失敗が残る場合は次の呼び出し境界で設定済みの長い実装用モデルへ一度引き継ぐ。引き継ぎ後も無進展なら停止規則を維持する |
| 再試行の実行 | レビュー側が進展による続行を許しても、ディスパッチ側には古い固定回数が残った | レビュー・事前確認・ディスパッチで同じ予算判定を使う。3回の修正を経て完了する実Nodeテスト付き回帰ケースを追加する |
| 検証の前提 | 読み込めないモジュールのまま多数のブラウザー検証を生成した | 実際のNodeテスト失敗を先に実装へ返す。Nodeテストだけで画面の成功を証明しない |
| 検証コードの受け渡し | モデルが改行の二重エスケープをJavaScriptの文の間へ出した | 生成時はソースの行配列を使用し、文字列リテラルを書き換えずに結合する |
| 検証ヘルパー | モデルがrunTestsを空の関数で再宣言した | ホストのヘルパーを同じ字句スコープのconstで固定し、再宣言を構文段階で拒否する。assert・Playwright expectは実行したassertionを計数する |
| エラーの所有者 | プロジェクトのimport時のReferenceErrorを、検証コードの誤りに分類できた | 実際のプロジェクトのスタックフレームと検証コードを区別する。検証自身の失敗をアプリの修正へ流さない |
| 成功済みの再開 | 古いPASSが残ると、新しい条件や変更済みソースの検証を飛ばせた | 現在の条件で再評価し、検証時の対象ファイルSHA-256と照合する。失効した場合は読み取り専用の検証を再実行する |
| 想定外の例外 | ModelFailure以外の例外でRUNNINGを残せた | 所有権を解放し、途中経過と停止理由を保存して再開可能にする |
| 自動検証の対象 | HTML/JSが混在する既存のフレームワークや他言語の工程へ静的サーバーを適用できた | 既存の依存パッケージや他言語のソースがある場合はこの自動変換の対象外にする |
| 文法制約後の無進展 | 実モデルがJSON末尾の閉じ括弧を出さず、構造上の空白を12,288トークンまで生成し続けた | JSONの構造上の空白を禁止し、文字列内の空白は維持する。新規ファイルだけのバッチは、承認された各パスを順番に1回ずつ書く文法にする |
| 同一操作の重複 | 同じ内容の新規ファイル書き込みが重複したため、正常な他の操作まで拒否された | 全く同一で中間操作のない重複だけを正規化する。異なる内容の競合書き込みは拒否する |
| 計画の設計情報 | 承認したassumptions・required_contextが実装へ渡らず、UIとロジックでAPIの前提が異なった | 設計情報を実装契約へ含める。元の依頼を優先し、設計情報で操作範囲を拡大しない |
| 証拠の重複 | 読み取り専用実行Taskの検証結果を、自分自身へもう一度マージした | 異なる実行Taskだけをマージし、操作・テスト実行を重複計上しない |
| 検証の意味 | 複数回のfillを追記だと思う、現在の結果要素を全履歴だと思う、存在しないaccessible nameを使う検証が生成された | 新しい検証を実行してから採用する。失敗したブラウザーassertionは別の計画用モデルで元の依頼・実ソースと照合し、実ソースの欠陥を示せない検証をソース修正へ流さない |
| 検証での画面改変 | スマートフォン検証がbodyのoverflowをhiddenへ変更していた | page/locatorのevaluate観測中の同期DOM・CSS変更を検出して検証コードのエラーにする。これはOSレベルのサンドボックスではない |
| 古い検証エラーからの再開 | 過去の不正な検証が2件あるだけで、検証器修正後の明示的な再開も拒否した | 検証生成側の有限な修復ループへ戻す。古いレポートを削除せず、実装の完了・権限・復旧epochを書き換えない |
| 検証モデルの無進展 | 実装用モデルが検証内の同じ文字列を繰り返し、出力上限に達した | 検証設計は計画用モデルへ渡し、不正な応答は別の実装用モデルへの限定した引き継ぎを行う。検証の応答・使用モデル・失敗診断を保存する |
| 検証修復の情報漏れ | 修復済みの検証コード・失敗理由が次の別の条件へ引き継がれ、前の検証を別の条件IDへ流用した | 検証を採用した時点で、その条件の失敗コンテキストを解消する |
| 期待値の弱体化 | 再生成された検証が等値比較を緩い範囲チェックへ変更して、誤ったアプリでも成功できた | 修復後に成功したブラウザー検証も、元の要求をまだ検証しているか照合する。単なる自己比較・履歴自身から期待履歴を作る検証は受け入れない |
| 改善の見落とし | Nodeの成功数と画面の成功項目数を合計しており、新しい画面挙動が成功しても別の誤ったテスト期待値が露呈すると進展なしになった | 同じ検証契約で新たに成功した項目と、テスト成功数の最高値を追跡する。過去の成功を取り戻すだけでは追加枠を与えず、追加枠の総数にも上限を設ける |
| 検証の短絡 | 完全な画面検証があるのに、修正後のNode失敗で画面検証を実行せず改善を観測できなかった | 完全な検証が保存済みならNode・画面の両方を実行する。検証を生成する前の一時的なNode事前検証とは区別する |
| 明示された検証 | 既に指定された検証コマンドを自動検証の生成で置き換えられた | 既存の検証実行器を保持する。自動生成は実行器がない場合を補う |
| 計画の出力量 | 複数ファイルの計画にも通常チャットの出力量上限が適用されていた | 計画の構造化生成に8,192トークンを渡す。無効な途中JSONを実行計画にしない |
| ソース文字列の破損 | 生成ソース内の文字列リテラルにある `</think>` も推論ブロックの終了として切り捨てられた | 応答先頭の推論ブロックだけを除去し、JSONや生成ソース内の文字列を保持する |
| 修復用コンテキスト | ブラウザーの長いスタックで、入力・検証コード・実際値が短縮上限の外へ落ちた | 失敗したチェック・入力値・画面の値・実際値と期待値を別の構造化フィールドで保持する |
| assertionの位置 | assertionを計数するラッパーのスタックだけが残り、修正すべき比較が分からなかった | 実行位置を検証ソースへ戻し、失敗したassertionの式を記録する |
| 同一パッチの反復 | 実モデルが修正理由を書いても、変更前後が同じパッチを返した | 小さな承認済みファイルでは次の呼び出しを全文writeへ切り替え、現在の選択モデルによる短い診断を一度挟む。診断は提案に限り、操作範囲・変更前ハッシュ・元仕様の検証を維持する |
| 小さなファイルの修正 | 最低32文字という短縮ガードが、10文字から10文字への正当な全文更新も拒否した | 元ファイルの半分未満への短縮を拒否する相対条件へ変更。大きなソースの切り捨ては引き続き拒否する |
| 内容を伴わない進展 | 表示順の変更や未使用関数の追加でファイルは変わっても、同じ仕様違反が続いた | 同じ検証契約・epochで失敗項目と成功項目を比較し、改善しない修正は設定済みの長い実装用モデルへ引き継ぐ。診断を挟み、工程中は引き継ぎ先を維持する。引き継ぎの追加枠は一度だけ |
| テスト追加による続行枠 | 13/13成功から、無関係なテストを追加して14/14成功させるだけで、画面が失敗したまま続行枠を得た | 同じ登録テスト総数における成功数の最高値と、独立検証で新しく満たした項目を用いる。テストの追加・過去の成功の取り戻しだけでは続行枠を増やさない |
| 承認状態の再解釈 | 修復の診断へ元の依頼を渡すと「まず計画、承認後に実装」を新たな指示として解釈し、計画と承認依頼を再出力した | 診断のsystemメッセージで計画・承認は完了済みと明示する。元の依頼は要件として引用し、失敗した条件を別途抽出する |
| 初回の検証と修正枠 | 最初の読み取り専用チェックも、ソース修正の試行回数に入っていた | 自動修正が承認された統合検証では、実際に失敗した最初の読み取り専用検証に対して一度だけ枠を補う。epoch間では持ち越さず、繰り返し検証しても増やさない |
| 推論ありの最終回答 | Ornithのテンプレートはプロンプト末尾に`<think>`を含むため、生成結果に開始タグがなく、推論の終了を取り出せなかった | 明示的な推論あり・非構造化呼び出しでは、閉じタグ以降だけを最終回答として返す。途中の推論だけで上限に達した場合は可視回答として扱わず、JSON内のタグ文字列は保持する |

## ネイティブ生成環境

### 2026-10-16の再開時に追加で確認した境界

| 境界 | 実際に確認した問題 | 修正 |
|---|---|---|
| 新規依頼の分類 | 昼食ルーレットの原文が、末尾の条件付き修正指示によりFIXになっていた | 新しいアプリを作る主目的を優先し、既存アプリ修正・単なるテスト追加とは区別する |

| ソース分離と工程分離 | 別ファイルを指定した正当な計画も、UIとロジックが別工程でないため拒否された | 宣言されたファイル境界でも仕様を満たすと判定し、不要な工程を強制しない |
