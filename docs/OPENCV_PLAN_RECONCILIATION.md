# OpenCV plan reconciliation

Reviewed: 2026-10-01 (V12 third source-to-code review)

This records the decision from comparing the original attached `Pasted text.txt` OpenCV instructions with current OLCR code, then checking that decision against the working implementation plan and current source. The source requirements include V1 continuous bounded capture (lines 380–405), V2 change signals (409–429), V6 OpenCV temporal state (536–566), V7 APC targets/transitions (570–627), V8 compute depth (631–652), perception telemetry (1770–1795), fixed-30-vs-adaptive ablation (1915–1940), and hackathon scope (2303–2333). The working implementation plan remains [V3](OLCR_UNIFIED_ARCHITECTURE_IMPL_PROMPT_V3.md); status evidence remains in [the implementation ledger](OLCR_UNIFIED_IMPLEMENTATION_STATUS.md).

## Decision

Keep OpenCV as the hackathon visual-state engine, but extend the existing ScreenCaptureKit and `PerceptionController` paths. Do not add a second capture scheduler, perception state machine, optical-flow implementation, or action-verification system. The existing-stream rate-update path is wired to APC revisions for macOS 14+ behind a runtime OS check; a healthy, explicitly grounded OpenCV track now leases APC L2/HIGH and requests its existing 20 fps target. A 5-second renewable lease ends on track loss/stop or expires without heartbeat. This is code-level policy wiring, not live rate/cost validation, and no cost-based gate is implemented yet. On macOS 13, retain truthful fixed 2 fps capture; no frame rate is promised there.

## Refreshed decision

The second pass found no reason to add another OpenCV primitive or perception subsystem. The important implementation gap is evidence: adaptive FPS is already wired from APC to the existing ScreenCaptureKit stream on macOS 14+, while achieved callback rate, dropped frames, capture/CPU cost, and task success remain unverified. Keep the OpenCV feature as the hackathon path and keep the portable feature-off fallback until packaging is solved.

## Latest compact telemetry addition

The existing APC snapshot now separates known event wakeups (AX, scroll, click/trigger, observed expected effect, grounded-track start) from pixel-derived `pixel_change`/`scene_change` wakeups. Both saturating counters flow through the existing observation-bound advisory World State policy update. Policy revision changes persist immediately; counter-only deltas within a revision are coalesced to at most one advisory update per second. Stable-frame and track-stop signals do not increment these counters; minor nonzero pixel-change signals are still counted as pixel wakeups. Capture notices/status expose a saturating per-session cumulative OpenCV timer covering both the existing `estimate_change` change/scene/ROI call and grounded `OpenCvFlowTracker::update` intervals; rolling p50/p95 remains separate for the detector and LK tracker. A Graphify-backed source-path review supported extending these existing APC/capture surfaces instead of adding another telemetry subsystem or per-frame store. The OpenCV total does not include capture/acquisition, conversion, IPC/UI, OS CPU, ScreenCaptureKit overhead, dropped-frame counts, OCR/Vision calls, or end-to-end task cost; the V7 task ablation and live supported-OS run remain open.

This review confirms that the existing grounded-control tracker already implements the user's button-tracking idea, and that the next OpenCV work should close remaining evidence gaps before adding more vision primitives.

Keep three costs distinct in all claims: **capture cadence** (how often ScreenCaptureKit delivers frames), **frame compute depth** (which OpenCV/recognition stages run), and **payload/model traffic** (what JPEG/semantic requests leave native capture). A healthy button track currently reduces JPEG/UI-Venus refresh traffic, not in-memory frame acquisition; LK requires new frames to track motion.

**Adopt adaptive capture rate as a core OpenCV-hackathon feature, with evidence gates.** The existing APC selects 2/8/20/30 fps policy targets for IDLE/ACTIVE/HIGH/BURST and calls `SCStream::update_configuration` on macOS 14+ without restarting the stream. Keep this path and the current 2 fps baseline. These values in `PerceptionRates::default()` are internal defaults, not user-configurable settings; treat them as tuning parameters and change them only after matched measurements. macOS 13 remains supported with a 2 fps capture ceiling while its compute policy still changes.

The implementation has not met the full V7 behavior or acceptance bar. A later permission-on isolated run successfully started and stopped ScreenCaptureKit capture twice, and a same-bundle relaunch captured without another picker confirmation; a newly built isolated bundle still triggered the macOS direct-screen/audio picker-bypass confirmation. Stable consent behavior for the installed app identity and capture of the correct target window remain unresolved. There is still no live supported-OS rate-transition, achieved callback-rate, dropped-frame, capture-cost, or end-to-end task-success evidence. The deterministic, in-process synthetic replay compares the same six-second visual sequence under fixed 30 fps and APC-selected capture cadence; it validates ROI change observation, transient/persistent detection delay and image-pipeline processing time, but does not simulate ScreenCaptureKit callbacks, operating-system CPU cost, action execution or task success. Do not report a target rate as an achieved rate.

### 2026-10-03 replay revalidation

The OpenCV-enabled replay was repeated five times on arm64 macOS 26.5.2. It processed 181 fixed-rate versus 35 APC-adaptive synthetic frames; median summed change-pipeline wall time was 0.905 ms versus 0.156 ms. Both schedules observed the transient ROI immediately and the separate fixture pixel-oracle effect in 16.3 ms. Adaptive cadence observed the persistent ROI 166.7 ms later in this fixture. Full samples and limits are in [the replay report](../benchmark_results/perception/v7_apc_opencv_replay_20261003_5x.md).

This confirms deterministic scheduling and fixture behavior only. It does not establish achieved live FPS, task success, CPU/power/capture savings, dropped frames, or model-call reductions. Existing one-second periodic animation can also phase-lock at the 2-fps idle cadence and become invisible in replay, so animation aliasing remains an explicit risk. P9/V7 stay PARTIAL pending supported-OS capture and matched action/postcondition measurements.

Adopt this remaining work, in order: (1) record a real supported-OS transition and cost once capture permission is available; (2) extend the synthetic fixed-30/adaptive replay into the plan's end-to-end task-success comparison, then run physical capture separately; (3) wire known OLCR scroll-action events into the existing `scroll` signal if/when a desktop scroll action is added to an existing executor path. Received/processed/skipped-frame counts, APC state duration, separate event/pixel wakeups, and cumulative OpenCV change-detection time now use existing telemetry surfaces; do not add per-frame heavyweight persistence. A bounded visual-HIGH guard is now implemented and unit-tested, but its 5-second maximum plus 5-second cooldown still needs animation fixture and live tuning evidence.

Do not adopt always-on 30 fps, a speculative cost-threshold governor, or a replacement scheduler. BURST remains short and rate-limited, HIGH remains event driven, and any future cost governor should use measured drop/CPU/capture data with an explicit fallback policy. Do not remove the macOS 13 path to simplify adaptation.

## Adaptive frame-rate implementation decision

1. Preserve 2 fps as the macOS 13 compatibility ceiling and initial stream baseline. Treat 2/8/20/30 as internal default policy targets, not achieved rates or user-configurable values.
2. The macOS 14+ update path is now wired to APC state changes on the existing `SCStream`, runtime-gated and clamped to 2–30 fps. Older stale policy revisions are ignored; an equal revision may retry a prior failed platform update. APC owns state hold/cooldown and the capture manager tracks the applied revision. Configured FPS is reported separately from observed callback-arrival FPS.
3. Before claiming adaptive-rate acceptance, validate a real macOS 14+ transition and compare requested/configured/observed rates with dropped frames and capture cost. No cost-based gate or live rate measurements are currently recorded. On macOS 13, continue reporting the actual 2 fps ceiling. APC now schedules the bounded OpenCV L0/L1 split, and a grounded track leases L2/HIGH (20 fps target) until stop, loss, or lease expiry. General L2–L4 work/forwarding remains request-driven. Only healthy OpenCV tracking currently suppresses JPEG/UI-VLM pulls. Do not simulate a higher achieved frame rate by relabeling or duplicating frames.
4. Keep 2/8/20/30 as internal `PerceptionRates` policy defaults for now. The original asks for configurable starting rates, but the current values are only injectable through Rust construction/tests, not persisted or user-configurable. Adopt user/runtime configuration only after matched supported-device measurements establish safe bounds; until then, tune the typed defaults through matched benchmarks. Preserve a small queue and discard stale work rather than accumulating frames.
5. Run fixed-30 and adaptive policy comparisons on the same replayable frame/task set first. The initial repeatable synthetic visual-control replay is recorded at [V7-REPLAY-01](../benchmark_results/perception/v7_fixed30_adaptive_replay_20261001.md); it passes ROI-detection and frame-reduction gates but does not complete the planned task-success ablation. A live capture-rate claim requires a separately identified OS/device run.
6. Exercise repeating small and large animation fixtures against the implemented 5-second visual-HIGH maximum/5-second cooldown; tune the defaults against false-HIGH duration and task responsiveness.
7. Keep the implemented aggregate received/processed/skipped-frame and APC state-duration telemetry, bounded callback-FPS and change-detector/LK timing samples, plus named `event_wakeups`, `pixel_change_wakeups`, and per-session cumulative `opencv_processing_ms`. These reuse the existing `PerceptionSnapshot` and capture status/frame notices; do not add per-frame persistence or another telemetry store. The OpenCV total covers `estimate_change` and grounded LK `OpenCvFlowTracker::update` intervals when the feature is enabled; feature-off reports zero for this OpenCV-only metric. Policy revisions persist immediately, while same-revision counter-only advisory updates are coalesced to at most once per second. Neither counters nor timings measure OS wakeups/drops or CPU/capture cost. Add end-to-end task cost and semantic-call attribution through existing observability only if replay evidence needs it.

This separates three controls that the original plan groups under adaptive perception: how often ScreenCaptureKit produces frames, which OpenCV/recognition stages process each frame, and which image/model payloads cross into the UI/backend. APC target revisions now wire frame rate to physical configuration on supported macOS 14+ systems and compute level to OpenCV's L0/L1 change/ROI work plus a leased L2 grounded track. The UI reports change-detector and rolling LK-update p50/p95 separately; the latter is bounded to 120 finite tracker-update timings. The mandatory replay currently supplies AX/click/expected-effect events at scripted times and checks known changed-ROI detection; it is a policy/image-pipeline schedule test, not an event-source test, task execution or independent postcondition test. Live effectiveness and costs remain unmeasured. Higher-cost LK still requires an explicit grounded track, OCR/UI-Venus remain request-driven, and healthy tracking suppresses JPEG/UI-VLM pulls while capture frames continue in memory.

## OpenCV link and packaging finding

The Rust OpenCV crate's default system probe linked 57 Homebrew OpenCV modules into the test executable, even though this tracker needs only the `video`, `features`, `imgproc`, `geometry`, `flann`, and `core` modules directly. Setting `OPENCV_LINK_LIBS` to those six modules builds the opt-in tracker and passes its focused tests (3/3); `dnn` can be omitted from the executable's direct link list, although Homebrew's `libopencv_video` still declares it as a runtime dependency. The `tauri:dev:opencv` launcher now applies this six-module override. This reduces direct module links; it does not make the app portable: Homebrew install names and transitive dylib closure still need to be copied/fixed-up, signed, and verified on a clean machine. Keep OpenCV opt-in and the release fallback unchanged until that bundle test passes.

The ScreenCaptureKit permission attempt for the exact signed current-source debug bundle was explicitly denied by macOS TCC. Because no capture callback/frame was received, the adaptive-rate path could not be exercised: the 2/8/20/30 policy targets, tracking-triggered L2/20 fps request, configured-FPS updates, callback-observed FPS estimator, dropped-frame behavior, and cost gate all remain distinct from live acceptance. Resume live rate and cost validation only after Screen Recording access has been enabled for the exact OLCR app identity; do not count configuration or a passing synthetic test as achieved FPS evidence.

### Animated-screen fixture extension

The existing detector/APC replay now includes small and large moving regions plus a phase-locked alias case. One deterministic run per build processed 361 fixed-30 frames; adaptive processing used 88 frames for the small animation in both builds, with no HIGH samples. The large animation used 81 frames / 65 HIGH samples with OpenCV and 51 / 30 with the feature-off detector. These are fixture-specific state and frame-count results, not a detector quality ranking. A one-second animation sampled at 2 fps in phase processed 25 frames and yielded zero observed changes, demonstrating that exact periodic aliasing can hide motion from the idle detector. This limit is recorded for future cadence decisions; no sampling-jitter policy was added. ## Anti-reinvention review

**BUILD_JUSTIFIED:** the APC transitions, cross-source provenance, task policy, and verification rules are OLCR-specific glue. Commodity capture, CV, OCR, AX, model routing, and verification stay with ScreenCaptureKit, OpenCV, Apple Vision OCR/AX, the existing UI-Venus route, and OLCR's existing verifier. The APC-to-platform configuration path is now wired for macOS 14+, but still needs live transition and cost validation. The main remaining implementation work is compute-selector scheduling and evidence—not a new state machine or vision library.
