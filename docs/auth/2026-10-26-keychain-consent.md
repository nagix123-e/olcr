# Keychainの再認証ループ修正

起動、Brainカタログのロード、外部ツール画面のマウントが、それぞれヘルパーによるKeychain読み出しを行っていた。失敗時にはフォーカスや再マウントによって再試行される。旧実装は読み出しを固定署名のヘルパー、保存をアプリ本体のkeyring経由で行い、保存時にヘルパーが内部に持つ移行済みマーカーを落としていた。このため一度の許可（Allow）しか与えられていない場合や、既存ACLがヘルパーを認めていない場合、認証ダイアログを繰り返す経路が存在した。

修正:

- ヘルパーの自動実行は `SecKeychainSetUserInteractionAllowed(false)`。起動や画面移動ではパスワード入力を出さない。認可がなければ専用エラーを返す。既存の呼び出し形式も既定で非対話になる。
- ネイティブプロセス内の共有キャッシュで、成功・失敗の両方を保持。並行する画面ロードも一度の復元結果を使う。明示的な「認証情報へのアクセスを許可」操作でだけ認証を再試行する。
- 読み書きとも固定パス・固定identifier・同じ証明書のヘルパーに統一。更新インストーラーはdesignated requirementを明示し、既存証明書・既存identityを維持する。アクセス権を全アプリへ開く変更は行わない。
- 保存はstdinで指定した1件だけを、プロセス間ロック下で読み込み・更新する。移行済みマーカーと他の認証情報を保持する。秘密値を引数や一時ファイルに渡さない。削除も同じ経路。
- OAuthトークンの背景保存は非対話。ユーザーが開始したサインインの完了時だけ対話を許可する。保存完了後にのみバックエンドのpendingバージョンへACKを返す既存動作を維持。

永続的な認可はアプリ内フラグではなくmacOS KeychainのACLが管理する。同じ署名の更新を同じプログラムと扱う根拠はAppleの [Understanding the Code Signature](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html) のCode Requirements / Keychain Access Controls。以前「Allow」のみを選んだ項目や未認可の既存項目は、明示的に許可を開始しmacOSで「Always Allow」を選ぶ必要がある。OSの認可を偽造して既存ACLを変更しない。Keychain自体がロック中なら解除は引き続きOSが管理する。

検証:

- `desktop/keychain-bridge/test_bridge.py`: 専用の一時Keychainとダミー値のみを使用。バイト列の異なる2つの同一署名ヘルパーで更新を再現し、非対話での再読込に成功。並行保存、マーカー維持、単一項目削除、不正更新拒否も確認。異なる署名要件の実行ファイルとロック済みKeychainはダイアログを出さず認可エラーで終了。テスト用Keychainパス指定はコンパイル条件付きで、本番バイナリには含まない。
- Rust: 全体113件成功、1件ignore。サンドボックス内では合成Visionテスト2件がOS APIエラーになったが、通常のmacOS環境で同じテスト一式が成功。認証関連6件とコマンド実行4件も成功。プロセスキャッシュの並行復元・失敗保持・明示再試行・更新反映・失敗書込時の保持、stdin経由の更新と既存の時間/出力上限を検証。
- フロントエンド35テスト成功、production build成功。ユーザー操作なしでの認可呼び出しゼロ、認可拒否後の自動再試行なし、背景OAuthと明示操作の分離を含む。
- 標準パスのヘルパーを同じ署名要件で更新済み。実ユーザーのKeychain値やパスワードを読み出していない。許可ACLも変更していない。
- 既存の別テスト用OLCRプロセスが起動していたため、AGENTS.mdの実機隔離ルールに従いGUIの起動・停止・操作は実施していない。稼働中のアプリ本体は置き換えず、ネイティブ/画面側の変更は次のアプリビルドで反映される。ヘルパーの非対話の既定値は既存アプリの次の呼び出しから有効。
