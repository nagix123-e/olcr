## 結論

操作の実行器を作り直す必要はない。既存の「新しい観測 → 計画 → ネイティブ実行 → 独立した結果検証」を維持し、その上に、目標・進捗・待機・復旧を管理するタスク実行層を加える。単に4回の上限を増やすだけでは、入力を含む仕事は自律化しない。

## 壊さない境界

- 既存のplan/native/verify APIと明示操作・slashコマンドを残す。新しいプランナーもこれらの実行器を呼び、座標やモデルの宣言だけで成功にしない。
- PID、bundle ID、ウィンドウ、AX session、capture session、観測鮮度、追跡フレームの一致を維持する。再開時は古いplanを再生せず再観測・再計画する。
- AXを優先し、座標が不足する操作は既存OCR/OpenCV経路を使う。既存adaptive frame rateと操作信号を再利用し、毎ステップ重い画像推論を必須化しない。
- 仮想カーソル、固定プレビュー、チャットスクロール、停止時のプレビュー消去、赤い閉じるボタン、Settingsと許可範囲を維持する。
- Browserは既存managed Playwright、nativeはAX/OpenCVが担当する。共通化するのは目標と進捗の管理であり、ブラウザー実行基盤を二重に作らない。
- 現在選択できるモデルとルーティングを維持する。新しいvisionモデルの追加や旧モデルの復元を、この計画の前提にしない。
- APIキー、OAuth、Keychain、macOSの権限をタスクが勝手に書き換えない。既存の許可内で実行し、未許可のOS操作では必要な操作だけを会話で案内する。

## 実装順序

### 0. 実GUIの基準を固定する

現在の追跡クリック、日本語入力、stop/close、スクロールを再確認し、build IDと同じ実行のログ・画面結果を保存する。既存のfixtureを再利用する。計画変更の理由になるのは最新の再現可能な失敗であり、過去の未解決表記だけではない。

実GUIはAGENTS.mdの隔離起動手順、最新絶対パス、READYとPID/profile/portの一致を守り、OpenCVは `OLCR_CUA_OPENCV=true` で有効化する。ユーザー用OLCRを終了しない。

### 1. チャット目標とタスク状態を追加する（最優先）

`main.tsx` と `chatComputerUseAction.ts` の分岐を小さな共通タスク入口へ接続する。既存の明示操作パーサーを優先し、それに一致しない操作目標を、現在の対象と会話文脈を使って構造化する。Web/E2E/通常の質問への誤分類を回帰検証する。

最小タスク状態は `task_id / conversation_id / goal / target / phase / verified_steps / budgets / cancellation`。状態はREADY、RUNNING、WAITING、BLOCKED、COMPLETED、FAILED、CANCELLEDとして記録し、会話上で見えるようにする。保存された進捗と、実際に実行できるネイティブセッションを区別する。再起動後は自動的に古い操作を継続しない。

バックエンドが目標・予算・検証済み進捗を管理し、ネイティブbridgeを持つクライアントが一手ずつ実行する。クライアントから送られた成功メッセージだけを完了の根拠にしない。操作前のcancel確認を共通化し、会話の停止やcapture終了後に次の操作が走らないようにする。

通常アプリ操作ではprojectを必須にしない。既存のprojectless会話を使い、projectはローカルソースのビルド・起動などworkspaceが必要な仕事に限って要求する。APIのproject必須条件も会話の認可と併せて変更する。

受け入れ条件：「Safariで検索して」のような指示を、設定済み許可内で、IDや絶対パスの入力なしにタスクとして開始できる。曖昧な複数対象のみアプリ名で確認する。

### 2. 目標プランナーを既存の操作種別へ拡張する

`app.py::_plan_native_chat_button_from_goal` と `computer_use.py` の検証を段階的に拡張し、一手としてpress_button、type_text、press_key、press_tab、scroll_wheel、open_disclosure、open_find、wait、complete、clarifyを選べるようにする。

現行のボタン専用schemaと経路は互換維持し、新しいschemaはactionごとに必要フィールドと根拠を検証する。フィールド名や操作対象は観測中の候補に束縛する。長い固定手順を一括実行せず、各手の検証後に目標を再評価する。

終了条件は表示文字だけでなく、フィールド値一致、フォーカス、開示状態、スクロール方向、ウィンドウ出現、ブラウザーURL/DOM等、各既存検証器が証明できる条件に広げる。局所操作の成功と最終目標の達成は別に判定する。入力値の秘密のreadbackは現行のboolean確認を維持する。

受け入れ条件：「検索欄に青い鳥と入力して検索し、結果を確認して」を1回の自然文から入力・Enter/ボタン・結果確認へ進める。入力済みなら同じ入力を重複実行しない。

### 3. 待機と復旧を加える

次の操作に進めない理由を、STALE_OBSERVATION、TARGET_CHANGED、TRACK_LOST、NOT_READY、UNVERIFIED_EFFECT、PERMISSION_REQUIRED、PLANNER_UNAVAILABLE、NO_PROGRESS等に分類する。まず待機または再観測し、同じ対象を確認してから再計画する。

既存verifierの単回利用を維持するため、遅延した結果は別のread-only再観測・条件評価で待つ。未検証の操作をただ再送しない。クリック・送信・文字入力の再実行には、すでに副作用が起きたかの確認が必要。

同じ対象・同じ画面状態・同じ操作が続く場合は無進捗として打ち切る。上限は操作数、復旧回数、全体時間、連続無進捗で持つ。最初は最大4操作の既存設定を維持し、実測後にタスク別予算へ拡張する。保存や送信などの副作用は単なるタイムアウトを理由に再実行しない。

受け入れ条件：遅れて表示される検索結果を待てる。追跡喪失ではfresh frameで再groundする。同じ失敗を無限に繰り返さず、完了・停止・必要な確認が会話上で区別される。

### 4. アプリ起動・E2E・終了を目標へ接続する

`computerUseTarget.ts` に、インストール済みアプリの表示名から実パス・bundle IDを解決する既存OSサービス利用を追加する。同名アプリや実行中の別パスは現行同様に区別する。許可されていないアプリは会話で選択・許可範囲追加へ進め、IDを手入力させない。

「このプロジェクトでE2Eして」は既存 `LocalE2EManager` とmanaged browserに接続する。既知のmanifest/package commandで起動できる範囲を先に扱い、任意shell生成へ広げない。nativeアプリの起動・通常Quitは別の構造化アクションとして足す。

所有情報を持ち、タスクが起動したプロセスだけを後片付けする。既存アプリを操作することと、終了する権限は区別する。対象アプリが変わる際にはsessionを再束縛する。

受け入れ条件：「このプロジェクトを起動して、フォーム入力を試して、結果を確認して、テスト用を終了して」が既存ランナーで動く。外部からattachしたサーバーやユーザー用アプリを巻き込まない。

### 5. 実測で必要になった操作だけを増やす

AXSetValue非対応の入力、チェックボックス/メニュー、キー組み合わせ、ドラッグ等は代表アプリで不足が確認されたものから追加する。仮想カーソルと既存target/freshness検証を使う。全操作を画像クリックへ置換したり、任意キー列・任意座標操作を先に全面開放したりしない。

## 完了判定

1. 未起動の許可済みアプリを自然文の名前で起動し、対象ウィンドウだけを表示・操作する。
2. 入力→検索→結果確認を、ユーザーがラベルや期待文字を逐一指定せず完了する。
3. 現在成功している動的ボタン追跡クリック・日本語入力・固定プレビュー・scroll/closeが回帰しない。
4. 遅延、無進捗、追跡喪失に対して、待機・限定復旧・明確な停止ができる。
5. チャット停止後に追加操作しない。再開はfresh observationから行う。
6. project E2Eの起動・検証・所有プロセスの停止を、既存ランナーで会話から行える。

最初の実装単位は1〜2の「1アプリ内の入力を含む目標ループ」。その後3の復旧、4のライフサイクルへ進む。新しいvisionモデル、macOS Allowの再調査、汎用shell実行、Settings全般の削除は、この自律性補強の先行条件にしない。
