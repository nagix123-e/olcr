# 201 FAIL・68 BLOCKEDのコード対応記録

## 対象と実施範囲

352件の改訂監査から FAIL 201件・BLOCKED 68件、計269件を対象にした。除外済みのINVALID_TEST 22件およびPASS 61件の監査結果は変更していない。ケース別対応は同名JSONの `cases` に記録した。

**この記録はコードの変更記録であり、269件の合格・解決を確認した記録ではない。ユーザー指示に従い、テスト、GUI E2E、ビルド、アプリ更新、プロバイダへの動作確認リクエストは実行していない。**

## 構成

- `external_tools.py`: 引数条件、同一プロバイダの複数取得、詳細取得、共通のJSON/SDMX/JSON-stat/USGS/BLS復号、HTTPの復旧。
- `app.py`: 取得済みのデータから回答を作る既存の所有者を使用し、通常・ストリーミング両経路の復旧と認証設定案内を維持。
- `runtime.py`: 既存の合成処理を再利用。外部データと代替ソースの本文から元の質問へ回答し、欠損・日時・単位・サンプルを区別する。
- 新たなルータ、プロバイダレジストリ、モデル配置、並列の回答サブシステムは追加していない。

## 共通原因の修正

1. 配列や深い入れ子を落としていた正規化を修正。空集合、クエリの反響、成功フラグ、件数だけを回答データと判定しない。秘匿フィールドを除外し、文字数・深さ・件数を制限する。
2. 比較対象は同じ取得経路で複数取得し、一部失敗を保存・表示する。比較の片側だけで要求全体を完了したように見せない。
3. 取得結果の見出しだけを回答にせず、既存の合成処理に元の質問と取得データを渡す。数値計算・通貨換算・画像の既存の型付き経路を維持する。合成に失敗した場合は取得済みデータを表示する。
4. JSON文字列を途中で切っていた推論入力を、構造を維持した有効なJSONに変更。出典を先に保持し、切り詰めと元の件数を明示する。
5. タイムアウト・接続失敗・短い429/502/503/504に対するGET再試行を1回に制限する。長いRetry-Afterを無視して連打しない。POSTの再試行は追加していない。
6. APIの対象外の要求は、誤った既定指標を返さず、設定済み検索へ切り替える。検索後も記事一覧で終わらず本文から質問へ回答する。代替根拠も取得できない場合は失敗を保存し、事実を生成して埋めない。
7. 認証未設定では設定カードを維持し、外部アクセス許可・Web autoの既存条件を満たす場合だけ公開資料による代替取得を試みる。秘密情報や設定は変更していない。

## 外部条件と実装の限界

元の68 BLOCKEDには複数エラーを持つケースもある。エラー出現数: CREDENTIAL_SETUP_REQUIRED=4, PROVIDER_BAD_RESPONSE=5, PROVIDER_EMPTY=27, PROVIDER_RATE_LIMITED=4, PROVIDER_TIMEOUT=14, PROVIDER_UNAVAILABLE=24。

通信回復や本文取得の経路は実装したが、外部サーバの停止、データの非公開、資格情報不足をコードだけで解消したことにはならない。検索の設定と有効な根拠、合成モデルが必要。未対応の詳細条件ではAPI機能を新設する代わりに代替ソース検索を用いている（例: 複雑なWikidata関係、BISの特定系列、UNHCRの集計、e-Statの地域・項目別統計、法令の全文・改正履歴、AISの実測集計、徒歩・自転車経路）。**代替検索が全269件の要求を満たすかは未確認であり、直接API機能の完成を意味しない。**

ランキングや傾向は取得した範囲を越えて断定しない。予報は観測と区別する。祝日から個別店舗の休業を断定しない。食材フィルタは記載材料に基づき、加工品等のアレルゲン確認を代替しない。
