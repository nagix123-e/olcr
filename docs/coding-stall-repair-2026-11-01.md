# コーディング処理の長時間停滞: 原因と修正

## 実際の停止事例

ユーザーが提示した献立アプリのTaskについて、既存アプリのログとSQLiteを読み取り専用で確認した。

- 計画用Bonsaiは約964秒で8192トークンの出力枠を消費し、回答JSONを返さず `output_limit` になった。
- 実装用Ollamaも約971秒で16384トークンを消費し、同じ理由で失敗した。
- その後、設定済みの複数APIを順に試した。利用できないモデルやアカウントがあり、一部は接続待ち120秒をアカウントごとに繰り返した。最後のBonsaiも8320トークンまで生成し、ユーザーの一時停止で終了した。
- モデル読み込み・入力処理・生成量は内部イベントに記録されていたが、Task取得APIとカードに出ていなかった。「0 / 2、実行中」のままに見える直接の表示原因だった。
- 別途、共有モデル実行枠を待つスレッドが停止要求に応答できないことを再現テストで確認した。

## 修正

1. **MLXで回答用の出力枠を確保。** 管理対象のコーディングで構造化出力を要求した場合に限り、推論に使うトークンを総出力枠の1/4、最大2048に制限する。上限では制約付きデコードで `</think>` に進み、同じ呼び出しのJSON生成を続ける。通常チャットの推論設定と、コーディングの総待機時間無制限の方針は維持する。
2. **Ollamaの推論だけが続く応答を検知。** 管理対象の構造化生成で、16384文字を超える推論を受信しても可視の回答が始まらなければ `reasoning_budget` として接続を閉じる。既存のフォールバック／再開処理に渡す。空白だけのcontentで検知を回避できない。GUIのログ監視がない呼び出しにも適用する。
3. **共有実行枠を待つ間の停止。** ロックの取得待ちで停止を確認し、他の実行の終了を待たずに中断する。取得済みのロックは必ず所有者が解放する。
4. **実際の進捗を表示。** 同じ呼び出しの最新進捗をTask取得APIに追加。カードにモデル読み込み、入力処理、生成量、切替理由、実行枠待ち、最終更新からの秒数、停止処理中を表示する。終了済みの生成量や前のモデルの値を現在の進捗として表示しない。生成量だけで工程を完了にしない。
5. **失敗理由を日本語・英語で説明。** コードの失敗と接続の失敗を同一視せず、推論予算と出力上限をカードとログで説明する。

接続先の可用性やユーザーが指定したモデル・アカウントの優先順は変更していない。すべての候補が利用不能なら、既存の停止・再開状態に移る。

## 検証

- 追加した不具合再現テストは修正前の失敗と修正後の成功を確認。
- コーディング関連: 303件実行、298件成功、5件skip。実ファイル操作・Node/Chromiumによる検証・再開・worktree・Taskルーティングを含む。
- モデル・推論・フォールバック・停止・進捗の関連テスト: 158件成功。実際のMetalとトークナイザーによるJSON制約テストを含む。
- コーディングカード／ライブログ: 30件成功。
- 実Bonsai: 推論ON・出力512トークンの小さな実装依頼をローカル実行し、約20秒・164トークンで1件の有効な書き込みJSONを生成。生成したsumモジュールをNodeで実行し、正負の入力を確認。
- TypeScriptチェックとproduction buildが成功。既存の大きなbundleに対する警告は残る。
- フロント全体: 440件中435件成功。今回変更していない地図3件、ModelsPanel 1件、ScreenCapture 1件の失敗が残る。失敗名は下記。
  - `ChatMap > opens an empty map with the entire world visible`
  - `ChatMap > fits one world closer when the unpinned map gets taller`
  - `ChatMap > can close during a pending WebKit zoom completion without touching removed panes`
  - `ModelsPanel > shows the active role as the starting point and allows other role selections in the shared chain`
  - `ScreenCapturePanel > starts only on request, refreshes on frame events, and clears the latest frame on stop`
- 独立レビューで指摘された空白応答、アカウント別ログの分離、通常チャットへの影響を再現テストで確認・修正し、再レビュー済み。
- 知識グラフを `graphify update .` で更新。

バックエンド全体は成功扱いにしていない。専用DBと必要なNode/Chromiumだけを用意した隔離環境でfail-fast実行し、255件中254件成功、`test_api.APITests.test_federal_data_uses_authoritative_terminal_renderer` が失敗した。期待する `AI notice` に対し、Web検索プロバイダー未設定の応答になった。今回変更していない外部データ／検索ルーティングのテストである。別の全体実行は、外部データのfixtureから実モデル推論へ入る未隔離経路があったため中断した。全体スイートの完走・全件成功は主張しない。

## 実機への適用範囲

既存のOLCRが起動しているため、AGENTS.mdの実機識別・既存プロセス保護の規則に従い、既存GUIへの操作、別GUIの起動、プロセス終了は実施していない。ユーザーDBは読み取り専用で調査し、テストは専用の一時DBで実行した。既存のTaskや作成途中のアプリは変更していない。

現在起動中のOLCRは旧ビルドである。修正したソースからの起動には、OLCRを終了した後で `scripts/start-dev-independent.sh` を使用する。元の献立アプリ依頼を実GUIで最初から完了まで実行する確認は未実施。
